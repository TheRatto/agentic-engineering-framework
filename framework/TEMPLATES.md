# Standard Templates

This document defines **mandatory output formats**
used by agents when producing deliverables.

Templates must be followed exactly.

---

## Planner – Feature Definition

### Feature <ID>: <Title>

#### Status
- todo / doing / review / test / done / blocked

#### Path
- full / lightweight (optional; default full)

#### Batch
- Optional. Comma-separated feature IDs if Coder may implement with others in one session (e.g. F-011, F-012)

#### Scope
- Bullet points defining what is included
- Explicit exclusions if relevant

#### Acceptance Criteria
- Clear, testable statements
- Written from a behaviour perspective

#### Tests Required
- What must be validated
- Type of testing expected (unit, integration, manual)

#### Notes
- Dependencies, assumptions, or open questions

---

## Coder – Implementation Report

### Feature <ID> – Implementation Report

#### What was implemented
- Bullet points describing completed behaviour

#### Files changed
- List of modified or added files

#### Tests
- Tests added or updated
- How to run them

#### Notes for reviewer
- Any trade-offs, concerns, assumptions, or follow-ups

---

## Reviewer – Review Outcome

### Feature <ID> – Review Outcome

#### Decision
- Approved
- Changes required

#### Blocking Issues (if any)
- Concrete issues that must be resolved

#### Non-Blocking Notes
- Suggestions or observations

#### DoD Check
- Acceptance criteria met: Yes / No
- Tests present: Yes / No
- Architecture consistent: Yes / No

---

## Tester – Test Report

### Feature <ID> – Test Report

#### Test scope
- What was tested
- Test environments or configurations (if relevant)

#### Results
- Pass / Fail

#### Issues found (if any)
- Description of the issue
- Steps to reproduce
- Expected behaviour
- Actual behaviour

#### Notes
- Any risks, edge cases, or observations

---

## Designer – Direction Proposal

### Feature <ID> – Design Direction Proposal

#### Candidate Directions
- Direction A: summary, strengths, risks
- Direction B: summary, strengths, risks
- Direction C (optional): summary, strengths, risks

#### Evaluation Matrix
- Usability: A/B/C score
- Differentiation: A/B/C score
- Accessibility: A/B/C score
- Implementation complexity: A/B/C score

#### Selected Direction
- Chosen option
- Why selected
- Why alternatives were not selected

#### Wireframe / Layout Notes
- High-level structure and interaction states

#### Handoff Notes
- Constraints and edge cases for Coder and Reviewer

---

## Designer – UX Rationale Entry

### Feature <ID> – UX Rationale Entry

#### Context
- Problem and user intent

#### Options Considered
- Option 1: trade-offs
- Option 2: trade-offs
- Option 3 (optional): trade-offs

#### Decision
- Selected direction and justification

#### References
- Link + relevance note

#### Validation Plan
- What to test and success signals

---

## UI Feature Gate Checklist (Reviewer / Tester)

### Feature <ID> – UI Gate Checklist

#### Design Artefacts
- UI-impacting feature: Yes / No
- Designer waiver documented (if applicable): Yes / No
- UI_SPEC.md aligned: Yes / No
- DESIGN_GUIDE.md aligned: Yes / No
- UX_RATIONALE.md considered: Yes / No

#### UX and Visual Quality
- Core flows are clear and testable: Yes / No
- Key states are represented correctly: Yes / No
- Accessibility expectations are satisfied: Yes / No
- Distinctive design intent preserved (or justified deviation): Yes / No

#### Notes
- Issues, risks, or follow-ups

---

## Documentation – Update Summary

### Documentation Update Summary

#### Docs Updated
- List of files changed

#### Reason
- What changed in the system

#### Notes
- Any follow-up or gaps identified

---

## Cleanup – Cleanup Report

### Cleanup Summary

#### Scope
- Areas or files cleaned up

#### Changes Made
- High-level description

#### Behaviour Change
- Confirmed unchanged

#### Remaining Debt
- Anything intentionally left untouched

## Runbooks (Optional)

Runbooks are execution aids generated by the Planner for specific features.
They provide copy/paste-ready agent prompts but do not replace the authoritative workflow.

- **RUNBOOK_SCHEMA.md** — structure for per-feature runbooks
- **RUNBOOKS_GUIDE.md** — guidance on when and how to use runbooks

## Artefact Schemas

The following schemas define the expected structure for project artefacts.
They are reference templates only and do not contain project-specific data.

### Planning & Status
- **PROJECT_BRIEF_SCHEMA.md**
- **PRD_GUIDE.md**
- **FEATURES_SCHEMA.md**
- **STATUS_SCHEMA.md**
- **CHANGELOG_SCHEMA.md**
- **UI_SPEC_SCHEMA.md**
- **DESIGN_GUIDE_SCHEMA.md**
- **UX_RATIONALE_SCHEMA.md**

### Architecture
- **ADR_SCHEMA.md**

### Security
- **SECURITY_REVIEW_SCHEMA.md**

Schemas should be referenced by agents when generating artefacts, but not duplicated.
